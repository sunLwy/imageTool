## 安全检测链路加固（utils/security.js + cloudfunctions/checkImage）
- 起因：用户反馈选图后偶发"内容安全检测暂时不可用"，原代码把 5 类失败（本地缩略图失败 / callFunction 失败 / imgSecCheck 偶发 -1 / 45009 额度超限 / 超时）全归一为 unavailable 且丢弃 errCode，无法定位
- 改动：错误码全程透传 + console.error；失败自动重试 1 次（间隔 1s）；45009 与 risky 不重试；同 path 会话级缓存安全结论（上限 50 条）；全链路 12s 超时兜底（修复 readFileSync 同步抛异常导致 Promise 永久 pending、loading 卡死的隐患）；缩略图 quality 0.8→0.7
- 云函数 checkImage 增加 console.error 输出 errCode/errMsg，方便云开发控制台定位
## 线上错误修复：callFunction "data exceed max size"（两轮，第一轮判断有误）
- 现象：真机选图后 `[security] 云函数调用失败: cloud.callFunction:fail Error: data exceed max size`
- **真实根因（第二轮确认）**：`wx.cloud.callFunction` 的 data 上限是 **100KB**（云开发官方社区回复"要求小于 100K"，CloudBase 文档：文本类型请求体 100KB），不是 1MB。base64 再放大 1.33 倍 → 高于约 75KB 的缩略图必挂。实测失败样本 base64 长度 307292（300KB），超限 3 倍
- 第一轮误判：按"约 1MB 上限"设计，预算设成 500KB 字符，750/0.7 首档就"通过预算"直接发出去 → 仍然必挂；教训：体积类上限必须查官方文档确认具体数值，不能凭印象
- 最终修复（utils/security.js）：
  - THUMB_PLANS 降到 520/0.5 → 440/0.45 → 380/0.4 → 320/0.35（520px 对 imgSecCheck 检出率无实质影响，该接口自身也是先缩到 750×1334 内）
  - B64_BUDGET = 90KB 字符（给 100KB 上限留 10KB JSON 包装余量），B64_HARD_LIMIT = 100KB，超了本地直接判失败不发无谓请求
  - 云侧仍报超限时自动降到最后最小档重试一次（自适应兜底）
  - 成功送检时 console.log 打出实际档位与 base64 长度，便于后续观察
  - exceed max size / thumb_too_large 标 noRetry=true，不浪费一次往返（SDK 自身还会重试 3 次）
- 备选方案备忘：① 官方 wx.cloud.CDN(data) 把大字段转临时 CDN URL 传参；② 改用云存储中转（uploadFile → 传 fileID → 云函数下载后送检），彻底摆脱 100KB 限制，也是将来迁移 mediaCheckAsync 2.0 的必经形态；当前 base64 小缩略图方案够用，暂不引入
